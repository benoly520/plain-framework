# Plain 开发工具链诊断多语言分析与方案

- 状态：中英文诊断已实现
- 分析日期：2026-11-13
- 范围：构建、编译器、契约检查及相关开发工具输出
- 支持语言：简体中文（`zh-CN`）、英文（`en`）

## 1. 结论

Plain 的诊断国际化采用“规则检测、结构化诊断、本地化输出”三层设计。
错误码、源码位置、严重级别、退出状态和自动修复行为不随语言变化；只有开发者看到的自然语言文案变化。

多语言不要求只能跟随操作系统。语言选择采用显式配置优先、环境变量其次、自动检测最后回退的策略。

## 2. 当前诊断链路

以 `PLAIN_E1202` 为例：

1. `src/lint.ts` 检测组件体中的派生快照问题。
2. Vite 插件将 lint 问题包装成 `PLAIN_E2001`。
3. `PlainCompileError` 组合错误码、文件、行列、详情和修复提示。
4. Vite、CLI、LSP 或 MCP 将诊断展示给开发者。

国际化不能只翻译 `src/errors.ts` 中的摘要；规则详情、动态参数、构建汇总、提示标签和修复建议都必须接入同一套文案系统。

## 3. 已有基础

- `src/errors.ts` 维护稳定的 `PLAIN_Exxxx` 错误码和 lint 规则映射。
- `src/lint.ts` 产生结构化位置、级别、错误码和自动修复信息。
- `src/compiler/index.ts` 的 `PlainCompileError` 提供 `code`、`file`、`line`、`column`、`detail`、`hint`，并支持 JSON 序列化。
- `src/vite/index.ts` 是构建期契约检查和编译错误的集中集成点。
- CLI、LSP、MCP 消费同一套规则链，适合复用消息目录。

## 4. 实现方案

### 4.1 统一诊断模块

`src/diagnostics.ts` 提供：

- `PlainLocale = 'zh-CN' | 'en'`；
- `resolveLocale()` 语言解析；
- 错误码摘要；
- lint 结构化消息标识、参数和中英文模板；
- 本地化格式化函数。

规则检测层不再决定展示语言。变量名、表达式、文件路径和命令作为参数原样保留，英文模板负责生成完整句子，避免拼接中文碎片。

### 4.2 编译器

`compile(source, fileName, { locale })` 支持语言配置。`PlainCompileError` 的详情、提示和 `Hint` / `提示` 标签按实例语言生成。
嵌套编译器辅助函数产生的错误也会在编译边界按同一语言重新格式化，不使用进程级可变“当前语言”。

### 4.3 lint

`check()` 保持原有调用兼容，并支持语言配置；规则消息以消息标识和参数保存。
`formatIssues(issues, fileName, locale)` 输出指定语言，同时保留自动修复对象和源码动态信息。
默认中文行为保持兼容。

### 4.4 Vite

插件支持 `locale` 选项：

```ts
import plain from 'plain/vite';

export default {
  plugins: [plain({ locale: 'en' })],
};
```

同一插件实例的契约错误、警告、编译器错误和构建汇总使用同一语言。终端与 Vite 错误浮层不根据浏览器语言再次切换。

### 4.5 CLI

支持：

```bash
plaindev build --locale en
plaindev check --locale zh-CN
plaindev check --locale=en
PLAIN_LOCALE=en plaindev check
```

CLI 解析语言值时不会把 `en` 误当成目录参数。帮助、检查汇总、自动修复提示和常见入口错误也支持双语。

### 4.6 LSP 与 MCP

LSP 支持实例语言配置；自动模式可以参考客户端初始化语言，再回退到进程环境。
MCP 复用结构化诊断和消息目录，不通过对话语言改变进程级全局状态。

## 5. 语言选择策略

优先级如下：

1. 入口显式配置，例如 CLI `--locale` 或插件 `locale`；
2. `PLAIN_LOCALE`；
3. `LC_ALL`；
4. `LC_MESSAGES`；
5. `LANG`；
6. 最终回退英文。

`auto` 表示继续执行环境检测。`en_US.UTF-8`、`en-US` 等形式归一化为 `en`；中文环境归一化为 `zh-CN`。
`C`、`POSIX`、空值和不支持的语言回退英文。

构建进程的环境不一定等于开发者物理设备的语言环境，因此显式配置对远程开发、容器和 CI 很重要。
不依赖 IP、时区、地理位置或业务应用语言推断开发者偏好。

## 6. 产物体积与依赖边界

结论是：**Plain 工具包可能略微增大，但使用 Plain 的业务客户端生产产物不应增大。**

| 对象 | 预期影响 | 原因 |
| --- | --- | --- |
| Plain npm 工具包 | 略有增加，实际增量以测量为准 | 增加翻译目录、语言解析和格式化代码 |
| 业务浏览器 JS | 不应增加 | 诊断只在构建阶段使用 |
| 服务端运行时产物 | 通常不增加 | 不依赖完整开发工具诊断模块 |
| Vite 开发错误浮层 | 文本长度可能变化 | 属于开发期信息，不是生产包 |

实现时必须保证：

- 浏览器运行时入口不导入诊断消息目录；
- 服务端运行时不通过公共入口反向依赖开发工具；
- 不把多语言文案注入生成代码；
- 不为诊断引入完整前端国际化框架；
- 只共享必要的错误码或类型，不共享完整翻译目录。

## 7. 不变性要求

同一份源码切换语言后，以下内容必须一致：

- 错误码及问题数量；
- 文件、行、列和严重级别；
- 自动修复操作及修复后源码；
- 构建退出状态；
- 成功编译时的业务产物内容和体积。

机器消费者不得解析中文或英文句子，应使用错误码和结构化字段。

## 8. 测试与验收

新增 `test/diagnostics-i18n.test.mjs`，覆盖：

- `PLAIN_E1202` → `PLAIN_E2001` 的中英文完整链路；
- 变量名、表达式、修复建议和命令保留；
- 中文和英文 lint 自动修复结果一致；
- 编译器实例语言相互隔离；
- CLI `--locale` 和 `--locale=en` 解析；
- `PLAIN_LOCALE`、`LC_ALL`、`LC_MESSAGES`、`LANG`、`auto` 和回退优先级；
- 浏览器运行时打包不包含诊断模块；
- 中英文成功编译产物的内容与体积一致。

正式发布前还应分别比较客户端 JS 的原始、gzip 和 Brotli 体积，并检查依赖分析清单。

## 9. 使用示例

直接使用编译器：

```ts
compile(source, 'App.jsx', { locale: 'en' });
```

显式中文：

```bash
plaindev check --locale zh-CN
```

自动读取环境：

```bash
PLAIN_LOCALE=en plaindev build
```
